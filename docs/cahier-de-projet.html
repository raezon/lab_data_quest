1. Contexte

« Vendredi noir, 21 h 14. Le site de LivrExpress reçoit quarante commandes par seconde. À 21 h 15, le serveur de base de données sature. À 21 h 20, le site répond “Erreur 500”. Quand tout redémarre, 1 312 commandes payées ont disparu, et personne ne sait lesquelles. »

LivrExpress est une entreprise algérienne de livraison de colis (Alger, Oran, Constantine, Annaba…). En cinq ans, elle est passée de 200 à 30 000 commandes par jour. Son système d'information, lui, n'a pas changé :

  • un serveur unique héberge le site web, la base MySQL et les fichiers ;
  • les factures PDF et bons de livraison sont enregistrés sur un partage réseau qui se remplit chaque mois ;
  • le site écrit directement chaque commande en base : si la base ralentit, le site ralentit ; si elle tombe, les commandes sont perdues ;
  • une facture écrasée par erreur est définitivement perdue ; il n'existe pas d'historique.

Après l'incident, Karim (directeur technique) décide de reconstruire la chaîne de traitement des commandes sur des services de données managés, sur le modèle d'AWS. Vous rejoignez l'équipe comme ingénieur·e cloud junior, aux côtés de Yasmine (données) et Mehdi (exploitation).

1.1 Le problème à résoudre

Problème constatéBesoin exprimé par l'entreprise
Le partage de fichiers satureUn stockage de documents sans limite pratique de capacité, organisé, avec nettoyage automatique des fichiers temporaires.
Factures écrasées ou supprimées par erreurPouvoir revenir à une version précédente d'un document.
Envoi de factures aux clients par e-mail en pièce jointePartager un document précis, pour une durée limitée, sans rendre le stockage public.
La base relationnelle unique ne suit plus la chargeUne base qui répond en temps constant quel que soit le volume, pour des accès simples et connus à l'avance.
Commandes perdues quand la base est indisponibleNe jamais perdre une commande acceptée, même si le traitement est en panne.
Un message mal formé bloque tout le traitementIsoler les messages défectueux sans arrêter la chaîne.

1.2 L'architecture cible

              [ File SQS : commandes-entrantes-dlq ]                     recus/<commandeId>.json

3. Phase 1 — Stockage objet (S3 / MinIO)

Objectif : remplacer le partage de fichiers par un stockage objet. À la fin de la phase, le bucket livrexpress-factures existe, est organisé par préfixes et protégé par le versioning.

1Comprendre le modèle

Avant toute commande, repérez dans la documentation ce qui distingue un bucket, un objet et une clé. Créez votre premier bucket avec l'outil de votre choix, puis observez-le avec un autre outil.

Piste : l'AWS CLI contacte le vrai AWS si on ne lui précise pas où se trouve le service.

2Organiser et décrire

Déposez plusieurs factures sous une arborescence par année et par mois, puis listez uniquement celles d'un mois donné. Ajoutez à un objet un type de contenu et une métadonnée personnalisée.

Piste : comparez le résultat d'un listage avec et sans délimiteur.

3Protéger et partager

Activez le versioning, provoquez un « accident », restaurez. Programmez le nettoyage automatique d'un préfixe temporaire. Générez un lien de téléchargement valable quelques minutes.

Piste : après une suppression, listez les versions de l'objet, pas seulement les objets.

4. Phase 2 — Base NoSQL (DynamoDB)

Objectif : stocker les commandes dans une table dont les temps de réponse ne dépendent pas du volume. À la fin de la phase, la table Commandes existe et vous savez l'interroger efficacement.

Changement de méthode. En SQL, on modélise les données puis on écrit les requêtes. En DynamoDB, on fait l'inverse : on liste d'abord les accès dont l'application a besoin, puis on choisit les clés qui les rendent possibles.

1Lister les accès

Avant de créer quoi que ce soit, complétez ce tableau pour LivrExpress.

Retrouver une commande par son identifiant
Lister toutes les étapes de livraison d'un colis, dans l'ordre
Lister les commandes en attente

2Créer, écrire, lire

Créez la table, insérez quelques commandes, relisez-en une par sa clé. Observez le format JSON « typé » des attributs.

Piste : seuls les attributs de clé se déclarent à la création ; les autres sont libres.

3Interroger sans tout parcourir

Répondez à une question métier de deux façons : en parcourant toute la table, puis en ciblant une partition. Comparez le nombre d'éléments examinés et renvoyés.

Piste : la réponse de l'API contient deux compteurs distincts.

5. Phase 3 — Files de messages (SQS)

Objectif : découpler le site web du traitement. À la fin de la phase, la file commandes-entrantes existe et vous maîtrisez le cycle recevoir → traiter → supprimer.

1Envoyer, recevoir… et recevoir encore

Envoyez un message, recevez-le sans le supprimer, puis tentez de le recevoir à nouveau immédiatement, et encore une minute plus tard. Notez ce que vous observez à chaque fois.

2Isoler les messages toxiques

Créez une file de quarantaine et reliez-la à la file principale. Faites échouer volontairement un message assez de fois pour qu'il y bascule.

Piste : la liaison se configure sur la file source, pas sur la file de quarantaine.

3Garantir l'ordre

Comparez une file standard et une file FIFO en envoyant une séquence numérotée. Observez le rôle du groupe de messages et de l'identifiant de déduplication.

6. Phase 4 — Projet final : le worker

« Jour J. Le site va publier de vraies commandes dans la file. Ton programme les lit, les enregistre, dépose un reçu, et ne perd rien. Même si on le coupe au milieu. » — Karim

6.1 Cahier des charges

Le squelette se trouve dans projet/pipeline/main.go. Les connexions aux trois services sont écrites ; la boucle principale et l'ordre des opérations aussi. Vous écrivez les fonctions marquées TODO.

Réf.ExigenceContrôle dans CloudQuest
E1Chaque message de commandes-entrantes est décodé en une commande (commandeId, client, montant, ville).Défi « Mise en production du worker »
E2La commande est écrite dans la table Commandes avec le statut TRAITEE.
E3Un reçu JSON contenant au moins commandeId est déposé sous recus/<commandeId>.json dans livrexpress-factures.
E4Le message n'est supprimé qu'après le succès de E2 et E3. À la fin, la file est vide.
E5Un message dont le corps n'est pas un JSON valide, ou dont le montant est ≤ 0, n'est ni enregistré ni supprimé.Défi « Résister aux données toxiques »
E6commandes-entrantes est reliée à commandes-entrantes-dlq (5 réceptions au plus) ; les messages rejetés y aboutissent.
E7Un message défectueux n'interrompt jamais le programme : les commandes valides du même lot sont traitées.

6.2 Parcours guidé

1Lire avant d'écrire

Lancez le programme tel quel : go run ./projet/pipeline. Que vous dit-il ? Lisez ensuite main() et traiter() : dessinez sur papier le chemin d'un message, avec les deux sorties possibles (succès, rejet).

2Recevoir et décoder

Écrivez recevoir puis decoder. Affichez simplement chaque commande décodée, sans rien écrire ailleurs. Relancez : que deviennent les messages entre deux exécutions ? Pourquoi ?

3Enregistrer

Écrivez enregistrer. Vérifiez dans la table, avec la CLI, qu'une commande apparaît avec tous ses attributs et le bon statut. Lancez le programme deux fois : combien d'éléments pour une même commande ?

4Déposer le reçu

Écrivez deposerRecu. Vérifiez l'objet dans la console MinIO : sa clé, son contenu, son type.

5Acquitter

Écrivez acquitter en dernier. Cliquez « Envoyer les commandes du jour » dans l'application, lancez le worker, vérifiez.

6Résister

Écrivez valider, complétez rejeter, branchez la DLQ. Cliquez « Envoyer un lot piégé ». Mesurez le temps que met un message toxique à atteindre la quarantaine, puis cherchez comment le réduire.

Expérience obligatoire — la coupure. Ajoutez temporairement une pause de quelques secondes entre l'écriture DynamoDB et le dépôt S3. Lancez le worker et interrompez-le (Ctrl+C) pendant la pause. Relancez-le. Observez l'état de la table, du bucket et de la file, et reportez vos observations à la question Q16.

7.4 Glossaire

BucketConteneur d'objets S3, au nom unique.
Clé / préfixeNom complet d'un objet ; début commun à plusieurs clés, utilisé comme « dossier » logique.
Clé de partition / de triAttributs qui identifient un élément DynamoDB et déterminent son emplacement et son ordre.
GSIIndex secondaire global : une autre « vue » de la table avec des clés différentes.
Délai de visibilitéDurée pendant laquelle un message reçu est masqué aux autres consommateurs.
DLQFile de quarantaine recevant les messages qui ont échoué trop de fois.
IdempotencePropriété d'un traitement que l'on peut rejouer sans changer le résultat.
EndpointAdresse réseau de l'API d'un service.
